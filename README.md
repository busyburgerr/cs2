# CS2 Cases

Площадка CS2 с покупкой за реальные деньги: кейсы с анимированной прокруткой,
рулетка red/black/green, коинфлип, инвентарь с продажей дропа, пополнение баланса
через платёжного провайдера, проверяемая честность (provably fair) и панель
администратора с настройкой всей экономики.

- **Фронтенд** — Nuxt 3 (Vue 3, Tailwind, Pinia), SSR
- **Бэкенд** — Node.js, Express, Prisma, SQLite (в проде — PostgreSQL)
- **Админка** — часть Nuxt-приложения, `/admin`, доступ по роли `ADMIN`

---

## Быстрый старт

Нужен Node.js 20+.

**1. Бэкенд**

```bash
cd backend && cp .env.example .env && npm install && npm run dev
```

В PowerShell копирование конфига — `Copy-Item .env.example .env`
(для локальной разработки `.env` уже создан).

Отдельного шага настройки БД нет: при старте сервер сам применяет миграции,
а если база пустая — заливает демо-данные (44 предмета, 5 кейсов, администратор
и тестовый игрок). API поднимется на `http://localhost:4000`.

Чтобы вместо демо-набора получить все официальные кейсы CS2 с ценами Steam:

```bash
cd backend && npm run import:cases
```

**2. Фронтенд** (во втором терминале)

```bash
cd frontend && npm install && npm run dev
```

Сайт: `http://localhost:3000`, админка: `http://localhost:3000/admin`.

**Демо-доступы после сидирования:**

| Роль | E-mail | Пароль |
|---|---|---|
| Администратор | `admin@cs2cases.local` | `admin12345` |
| Игрок | `player@cs2cases.local` | `player12345` |

## Структура

```
backend/
  prisma/schema.prisma     схема БД
  prisma/seed.js           демо-данные (цены кейсов считаются из целевого RTP)
  src/lib/fair.js          provably fair: сиды, HMAC, диапазоны билетов
  src/services/opening.js  открытие кейса и продажа предмета (в транзакции)
  src/services/payments.js платежи: mock и Stripe
  src/routes/              auth, cases, me, payments, admin
frontend/
  pages/                   витрина, кейс, инвентарь, кошелёк, история, честность
  pages/admin/             дашборд, кейсы, предметы, пользователи, открытия, платежи
  components/CaseRoulette.vue  анимация прокрутки
  stores/auth.ts           сессия и баланс
```

Все денежные суммы хранятся и передаются **в минимальных единицах (центах,
копейках)**, целыми числами — никаких float-ов в расчётах баланса. Валюту
задаёт бэкенд (`CURRENCY`), фронтенд подхватывает её сам через `/payments/config`.

## База данных: автомиграции

SQLite, схема применяется автоматически при запуске сервера:

1. `prisma migrate deploy` накатывает непринятые миграции. Если файла базы ещё
   нет, он создаётся вместе со всеми таблицами.
2. В разработке дополнительно сверяется `schema.prisma` с базой: если схему
   правили без миграции, таблицы догоняются через `db push`.
   В production этот шаг выключен — только версионированные миграции.
3. Если в базе нет ни одного кейса, заливаются демо-данные (кроме production).

Управляется переменными `AUTO_MIGRATE` и `AUTO_SEED` (обе по умолчанию включены,
`AUTO_SEED` — только вне production).

После изменения `schema.prisma` создайте миграцию для продакшена:

```bash
cd backend && npm run db:migrate -- --name add_something
```

Делайте это до того, как dev-сервер догонит схему сам: если он уже применил
изменения через `db push`, история миграций разойдётся с базой и `migrate dev`
предложит сброс. Тогда база уже соответствует схеме, и миграцию достаточно
записать вручную — положить SQL в `prisma/migrations/<timestamp>_name/migration.sql`
и пометить применённой:

```bash
cd backend && npx prisma migrate resolve --applied <timestamp>_name
```

После `prisma generate` перезапустите API: работающий процесс держит в памяти
старый клиент и не увидит новые поля.

## Каталог кейсов и цены Steam

В базе все 42 официальных кейса CS2 с реальным составом, картинками и ценами
торговой площадки Steam.

```bash
cd backend && npm run import:cases
```

| Флаг | Что делает |
|---|---|
| `--rate=83.45` | пересчёт цен из долларов в другую валюту |
| `--rtp=0.9` | целевая отдача кейса (по умолчанию 0.92) |
| `--keep-demo` | не отключать демо-кейсы из сидирования |

Шансы выставляются как в игре: Mil-Spec 79.92%, Restricted 15.98%,
Classified 3.2%, Covert 0.64%, нож или перчатки 0.26% — доля тира делится
поровну между предметами тира. Всего 1 000 000 билетов на кейс.

Цена предмета — цена на Steam для самого ликвидного износа, для которого есть
котировка (Field-Tested → Minimal Wear → Factory New → Well-Worn → Battle-Scarred).
Цена кейса считается из ожидаемой ценности дропа и целевого RTP, а не берётся
со Steam: реальная цена ящика ниже стоимости содержимого, и площадка на такой
цене работала бы в минус.

Источники — открытые датасеты
[CSGO-API](https://github.com/ByMykel/CSGO-API) (состав, картинки) и
[counter-strike-price-tracker](https://github.com/ByMykel/counter-strike-price-tracker)
(котировки Steam). Импорт идемпотентен: повторный запуск обновляет цены
и составы, не плодя дубликаты. Запускайте по расписанию, чтобы цены не отставали
от рынка.

Предметы без котировки на Steam пропускаются (обычно это редкие фазы ножей).

## Provably fair

Результат открытия определяется до нажатия кнопки и не зависит от того,
какой предмет выгоднее выдать площадке.

1. Сервер генерирует `serverSeed` (32 случайных байта) и публикует только
   `SHA-256(serverSeed)`. Подменить сид задним числом нельзя — хеш не сойдётся.
2. Игрок задаёт свой `clientSeed`, каждое открытие увеличивает `nonce` на 1.
3. Билет: `int(HMAC_SHA256(serverSeed, clientSeed + ":" + nonce)[0..13]) % totalTickets`,
   где `totalTickets` — сумма весов предметов кейса.
4. Предметы занимают непрерывные диапазоны билетов пропорционально весам —
   без округлений, поэтому результат воспроизводится точно.
5. По кнопке «Сменить серверный сид» старый сид раскрывается и записывается
   в прошлые открытия, после чего любой ролл можно пересчитать.

Калькулятор проверки встроен в страницу `/fair` и считает всё в браузере
через Web Crypto. Тот же расчёт на стороне сервера — в `backend/src/lib/fair.js`.

## Игровые режимы

**Кейсы** — прокрутка ленты предметов, шанс = вес предмета / сумма весов кейса.

**Рулетка** (`/roulette`) — колесо против площадки. Раунды идут по расписанию
независимо от того, есть ли игроки: приём ставок → прокрутка → выплаты → новый
раунд. Состояние живёт в БД, поэтому перезапуск сервера не рвёт начатый раунд.
Сектора чередуются красный/чёрный, зелёные распределены равномерно; количество
секторов и множители задаются в админке. Билет = `HMAC(serverSeed, "round:<номер>:0") % секторов`,
хеш сида публикуется в начале раунда и раскрывается вместе с результатом.

**Коинфлип** (`/coinflip`) — бросок монеты против площадки, результат мгновенно.
Использует ту же пару сидов, что и кейсы: билет = `HMAC(serverSeed, clientSeed:nonce) % 10000`,
победа при билете меньше `шанс × 10000`. Значит, любой бросок проверяется тем же
калькулятором на `/fair`.

Обе игры банкует площадка — второй игрок для партии не нужен, а маржа
предсказуема и настраивается.

## Экономика: настройка из админки

Раздел **Админка → Экономика** (`/admin/economy`) — единственное место, где
задаются деньги площадки. Значения лежат в таблице `Setting`, применяются
мгновенно (без перезапуска), а всё, что не задано, берётся из значений по умолчанию.

| Группа | Что настраивается |
|---|---|
| Кейсы | возврат при продаже предмета, сколько кейсов открывается за раз |
| Кошелёк | минимальное и максимальное пополнение |
| Рулетка | вкл/выкл, количество красных/чёрных/зелёных секторов, множители, длительность приёма ставок и прокрутки, лимиты ставки |
| Коинфлип | вкл/выкл, шанс победы, множитель выплаты, лимиты ставки |

Страница пересчитывает отдачу (RTP) и маржу прямо при вводе, до сохранения,
и подсвечивает красным настройки, при которых игра уходит в убыток.
На дефолтных значениях: рулетка — 93.3% отдачи (маржа 6.67% и на цвет, и на зелёное),
коинфлип — 95% (маржа 5%).

Фактическая маржа по каждому режиму видна на дашборде: оборот, выплаты и GGR
отдельно для кейсов, рулетки и коинфлипа.

## Экономика кейсов

Шанс предмета = его вес / сумма весов кейса. Шансы публичные, они видны
на странице кейса. В админке при редактировании состава сразу показываются:

- ожидаемая ценность дропа (EV),
- RTP при текущей цене (`EV / цена`) — красный, если кейс убыточен,
- маржа площадки на одно открытие,
- кнопка «Цена под целевой RTP» — считает цену от заданного процента отдачи.

Демо-кейсы засеяны с RTP 90–96%. Продажа предмета обратно возвращает
`SELL_RATE` (по умолчанию 90%) от его цены.

## Платежи

Провайдер выбирается переменной `PAYMENT_PROVIDER`.

**`mock`** — режим разработки. Платёж подтверждается вручную на странице
`/wallet/checkout`, реальные деньги не двигаются. В `NODE_ENV=production`
приложение откажется стартовать с этим провайдером.

**`stripe`** — приём реальных платежей:

```bash
cd backend && npm i stripe
```

```env
PAYMENT_PROVIDER=stripe
STRIPE_SECRET_KEY=sk_live_...
STRIPE_WEBHOOK_SECRET=whsec_...
```

Пополнение создаёт Stripe Checkout Session, баланс зачисляется **только**
из webhook `checkout.session.completed` на `POST /api/payments/stripe/webhook`
(подпись проверяется по сырому телу запроса). Зачисление идемпотентно:
повторный webhook денег не добавит. Локально webhook пробрасывается так:

```bash
stripe listen --forward-to localhost:4000/api/payments/stripe/webhook
```

## Что сделано для целостности данных

- Списание баланса и розыгрыш идут в одной транзакции с оптимистической
  блокировкой по `nonce` — параллельные запросы не могут потратить один тикет дважды
  (так же устроен и коинфлип).
- Ставка в рулетке списывается условным `updateMany` по балансу, выплаты
  начисляются один раз при закрытии раунда: повторный проход `tick()`
  не выплатит дважды, потому что раунд уже в статусе `SETTLED`.
- Продажа предмета защищена условным `updateMany` по статусу: двойная продажа невозможна.
- Зачисление платежа идемпотентно (переход `PENDING → PAID` атомарен).
- Каждое движение денег пишется в `Transaction` с балансом после операции.
- Кейс, который уже открывали, нельзя удалить — только отключить.
  Предмет, лежащий у игроков в инвентаре, тоже не удаляется.

## Перед запуском в продакшен

Технический минимум:

- [ ] `DATABASE_URL` на PostgreSQL и `provider = "postgresql"` в `schema.prisma`
- [ ] `JWT_SECRET` из `openssl rand -hex 32`, `NODE_ENV=production`
- [ ] HTTPS и перенос токена в `httpOnly`-cookie (сейчас токен читается JS-ом,
      чтобы фронтенд мог слать `Authorization` — при вынесении API на тот же
      домен это заменяется на httpOnly + CSRF-токен)
- [ ] реальный платёжный провайдер и проверка webhook-подписи (уже реализована)
- [ ] бэкапы БД и мониторинг расхождения фактического RTP с плановым

Юридический минимум (вне кода, но без него запускать нельзя):

- [ ] лицензия/разрешение на азартные игры в целевой юрисдикции —
      открытие кейсов за деньги регулируется, а в ряде стран (включая РФ) запрещено
- [ ] проверка возраста и личности (KYC), а не чекбокс «мне 18»
- [ ] AML-процедуры и лимиты, самоисключение и лимиты депозита для игроков
- [ ] публичная оферта, политика возвратов и обработки персональных данных
- [ ] CS2 и скины — товарные знаки Valve; площадка с ними не аффилирована,
      использование бренда нужно согласовывать
